По итогам рабочей встречи направляем предложение по разработке дополнительного модуля к действующей системе Cake Lab. Модуль выявляет устойчивые повторяющиеся покупки клиентов, фиксирует отклонение от привычного поведения и формирует событие для персонального уведомления. В предложение включены только факты, подтверждённые на встрече; неподтверждённые функции и гарантии не указаны.

1. Исходная ситуация

На встрече подтверждено следующее:

  1. У Cake Lab есть собственная система с открытым API.
  2. В системе уже применяется базовая кластеризация клиентов, в том числе по частоте покупок и факту возврата.
  3. Каналы обращений — приложение, сайт и Telegram-бот; обращения из всех каналов консолидируются в одной системе.
  4. Значительная часть типовых заказов автоматизирована, сложные заявки обрабатывают сотрудники.
  5. Рассматривается возможность более глубокого анализа индивидуального поведения клиентов.

2. Предлагаемое решение

Модуль работает поверх действующей системы и не требует её изменения: данные читаются через API, обратно передаётся событие. Последовательность работы:

ШагЧто происходит
1. История покупокМодуль получает историю покупок клиентов через API Cake Lab.
2. ПаттерныВыявляются устойчивые повторяющиеся покупки — например, определённый товар в определённый день недели.
3. ОтклонениеФиксируется расхождение с ожидаемым поведением: ожидаемая покупка не состоялась.
4. СобытиеПо согласованным правилам формируется событие для уведомления.
5. ПередачаСобытие передаётся в согласованный канал или ответственному сотруднику.

Правила и искусственный интеллект

Базовые закономерности («каждый вторник», «раз в две недели») обрабатываются прозрачными алгоритмическими правилами: порог устойчивости паттерна, допустимое отклонение по времени, момент срабатывания. Такие правила можно объяснить, проверить и настроить.

Целесообразность применения ИИ для сложных отклонений определяется после обследования данных, а не заранее. Решение принимается по качеству и глубине истории; сложные паттерны, если потребуются, выносятся в отдельный этап.

Подтверждённый сценарий

Клиент регулярно покупает определённый товар в определённый день недели. Когда очередная ожидаемая покупка не происходит и выдержано допустимое отклонение, система фиксирует событие и инициирует персональное напоминание о товаре. Правила устойчивости, допуск по времени, момент срабатывания и порядок отправки согласовываются с заказчиком на этапе обследования.

3. Что получает Cake Lab

  • Своевременное выявление изменений — изменение привычного поведения клиента видно в момент, когда оно происходит, а не по итогам отчётного периода.
  • Персональный повторный контакт — сообщение о конкретном товаре в конкретный момент вместо массовой рассылки.
  • Снижение ручного анализа клиентской базы.
  • Основа для программы удержания — база для последующих сценариев работы с клиентами.
Коммерческий эффект и точность зависят от качества данных и правил сценария и оцениваются по итогам пилота. Обещаний по показателям до обследования не даём.

4. Порядок работ

Этап 1. Обследование

Сроки и стоимость разработки не могут быть обоснованно названы до проверки данных и согласования правил. На этапе обследования:

ЗадачаРезультат
Владелец задачиОпределён ответственный со стороны Cake Lab, подтверждена бизнес-цель.
ДанныеИзучена документация API, оценены глубина, полнота и качество истории покупок.
ПравилаСогласованы критерии выявления паттерна и отклонения, порядок формирования и передачи уведомления.
ТребованияСогласованы требования к работе с клиентскими данными.
Границы пилотаЗафиксированы состав и критерии приёмки пилота.

Итог этапа: согласованное техническое задание, состав пилота, сроки, стоимость и план реализации.

Этап 2. Пилот

Ограниченный пилот на одном сценарии. Окончательный состав определяется совместно с заказчиком по итогам обследования и настоящим документом не фиксируется. Предполагаемый состав:

  1. Подключение к тестовому контуру API — без доступа к рабочим данным и без изменений в действующей системе.
  2. Обработка ограниченного, заранее согласованного среза истории.
  3. Один подтверждённый тип паттерна (например, регулярная покупка в определённый день недели).
  4. Фиксация отклонения и формирование события по согласованным правилам.
  5. Технический журнал срабатываний — результат пилота подтверждается записями журнала, критерии приёмки определяются на этапе обследования.

5. Риски и открытые вопросы

Открытые пункты вынесены в документ, чтобы обсудить их на встрече, а не обнаружить в ходе проекта.

Риски, допущения, зависимости

  1. Состав и качество данных API не подтверждены.
  2. Канал уведомления и возможность автоматической отправки не согласованы.
  3. Не определены правила выявления устойчивого паттерна.
  4. Не подтверждены правовые основания и согласия клиентов на коммуникации.
  5. Ответственный владелец проекта со стороны заказчика не установлен.
  6. Сроки, стоимость и показатели успешности определяются только после обследования.
